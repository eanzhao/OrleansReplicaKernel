# 从单节点内核走向多节点 runtime：第一条分布式切入线怎么选（第四十篇）

这一篇承接前面的 [38-replica-design-blueprint.md](./38-replica-design-blueprint.md) 和 [39-first-runtime-implementation-plan.md](./39-first-runtime-implementation-plan.md)，但不再停留在“应该怎么切”的抽象层。

它只回答一个更具体的问题：

> 从今天这个 `OrleansReplicaKernel` 出发，怎么走进多节点 runtime，而且不把单节点已经做对的东西全打散。

这个问题比看上去麻烦。因为一旦进入多节点，很多单节点里看起来很自然的边界都会开始变味：

- `GrainId` 还稳不稳
- `GrainAddress` 还是不是一个简单的本地映射
- activation 还能不能只靠一个本地字典
- routing 是不是还只是“找本地对象”
- 目录到底是缓存，还是事实源
- owner 失效以后，谁来接管

所以这篇不讲“大而全的分布式系统”，只讲第一刀该怎么切。

---

## 1. 先说结论

如果目标是从 `OrleansReplicaKernel` 进入多节点，我会先保留单节点已经证明正确的主干，再只补三类分布式部件：

- 目录从“本地映射”升级成“可失效的节点级目录”
- routing 从“直接拿 activation”升级成“先查目录再转发”
- runtime 从“只管本地调用”升级成“协调本地与远端消息”

这三步之外的东西，第一批都不要碰太多。尤其不要一上来就把 membership、placement、gateway、recovery、负载均衡全搅进来。

原因很简单：多节点不是一次性把所有分布式复杂度都打开，而是先把“本地语义不变，远端语义可插入”这个框架立住。

---

## 2. 现在已经够用的边界

`OrleansReplicaKernel` 现在已经有几条很宝贵的边界，这些边界应该尽量保留。

### 2.1 Identity 边界已经够用了

现在的 `GrainId` 和 `GrainAddress` 足够清楚：

- `GrainId` 表达“这个 grain 是谁”
- `GrainAddress` 表达“在什么节点上看见它”

这一层先不要重切。多节点真正需要变化的，不是 identity 本身，而是 address 的有效期和可达性。

### 2.2 Invocation 边界已经够用了

现在的 `IInvokable`、`IInvocationRuntime`、生成出来的 reference / invokable 壳，这条线已经能把调用协议和业务实现分开。

这条边界也先别动。多节点只会让 invocation 多一个“能否远端投递”的问题，不会改变它本身应该怎么表达。

### 2.3 Scheduling 边界已经够用了

`ActivationScheduler` 现在只管单 activation 的 turn 串行执行，这个边界非常值钱。

多节点以后，这个调度层还是应该保留不变。因为节点变了，activation 内部的串行语义不能变。

### 2.4 Host / Demo 边界已经够用了

现在的 `OrleansReplicaKernelBuilder`、`OrleansReplicaKernelHost`、`Program.cs` 也已经把“怎么装配、怎么启动、怎么演示”切开了。

这一层在多节点初期也不要重写。先让 host 学会挂多个节点实例，再说别的。

---

## 3. 哪些边界必须重切

有几块边界，如果不重切，单节点思路一旦进多节点就会卡住。

### 3.1 Activation Directory 不能再只是本地字典

现在的目录职责很单纯：

- 根据 `GrainId` 找 activation
- 没有就创建
- 有就复用
- 需要的时候卸载

这在单节点里是对的，但到多节点以后，目录必须开始表达“这个 activation 属于哪个 owner 节点”。

也就是说，目录不再只是“有没有”，还要回答：

- 这个 grain 当前归谁管
- 这个 owner 还活不活
- 目录缓存过期了没有
- 本地是不是只是一个旁路缓存

所以目录要从“本地表”重切成“节点级目录 + owner 语义 + 失效机制”。

### 3.2 Routing 不能再是直接拿 activation

单节点里，routing 其实很朴素：查目录，拿 activation，调用。

多节点以后，这个过程必须拆成两步：

1. 找 owner 或本地副本
2. 决定本地执行还是远端转发

否则 routing 会被迫同时承担目录、消息投递、重试、失效处理，这样很快又脏回去。

### 3.3 Runtime 不能再只管“本地调用成功”

现在的 runtime 只需要把消息送到本地 activation。

多节点以后，runtime 要开始协调：

- 本地消息
- 远端消息
- 回执
- 失效后的重试或重新定位

但注意，它还是不该直接吞掉 routing 和 directory 的职责。runtime 应该是协调者，不是大杂烩。

---

## 4. 第一批要引入的分布式部件

我会把第一批分布式部件控制在 4 个。

### 4.1 Node Registry / Membership 的最小形态

不用一开始就做完整 membership 协议，但至少要有一个“节点可见性”抽象。

它要回答：

- 当前有哪些节点
- 哪些节点活着
- 哪些节点已经不该再被选作 owner

这层可以先很朴素，关键是语义不能缺。

### 4.2 Distributed Directory 的最小形态

目录要从本地缓存升级为“按 grain 维持 owner 信息”的组件。

最小要有：

- owner 记录
- 本地缓存
- 失效
- 重新定位

这层先不追求强一致，但要明确它是“目录事实”的承载者，而不是某个 runtime 的内部小字典。

### 4.3 Message Transport 的最小形态

现在 当前原型 的消息还是“对象内调用”。

多节点一旦进来，就必须补一个最小 transport 抽象，让消息可以：

- 本地直达
- 远端投递
- 带请求 id 和返回通道

这里先别急着做真正网络协议。先把消息边界与传输边界分开。

### 4.4 Remote Activation / Forwarding 的最小形态

当 routing 找到的不是本地 owner 时，必须能把调用转发出去。

这一步不需要完整分布式容错，但至少要有：

- 本地调用
- 远端转发
- 结果回传
- 远端失败后的目录失效

这就是多节点的第一道门。

---

## 5. 单节点抽象怎么演进成多节点抽象

这部分是最关键的。不是加新东西，而是让旧东西自然长大。

### 5.1 `GrainAddress` 从“地址”变成“目标描述”

现在的 `GrainAddress` 很简单：节点名 + `GrainId`。

多节点以后，它最好继续保留这个形状，但语义要稍微换一下：

- 它不再只是“这次调用要去哪儿”
- 它更像“当前目录告诉我，这个 grain 在哪个节点上被看见”

也就是说，地址先不要变复杂，先把地址的来源变复杂。

### 5.2 `IActivationDirectory` 从“创建器”变成“目录 + owner cache”

单节点目录现在直接负责创建 activation。

多节点以后，最好把它演进成两层：

- 目录层：负责 grain owner、失效、重新定位
- 本地激活层：负责本节点 activation 的复用和卸载

这样以后就不会把“目录事实”和“本地对象生命周期”混在一起。

### 5.3 `IGrainRouter` 从“找 activation”变成“找执行路径”

路由最终要回答的，不是“这个 activation 在哪”，而是“这个调用该本地执行还是远端执行”。

这意味着 router 以后会多出几个判断：

- 目录指向本地还是远端
- 本地是否已有 activation
- 是否需要转发
- 远端失败后是否回到目录层重新查

### 5.4 `IInvocationRuntime` 从“调用协调器”变成“消息协调器”

多节点以后，runtime 还是不该直接承担业务路由逻辑，但它要开始管消息的完整生命周期：

- 组包
- 路由
- 传输
- 回包
- 超时
- 失效信号

这才是 runtime 的边界往外长了一步。

## 6. 最小多节点里程碑

如果要按最小可行步骤推进，我会这样排。

### 6.1 里程碑一：双节点本地模拟

先在同一进程里模拟两个节点，但语义上已经按节点分开。

验收标准：

- `GrainId` 能映射到 owner 节点
- 路由能判断 local / remote
- 本地节点能处理自己的 activation
- 远端调用能被转发到另一节点的目录和 activation

### 6.2 里程碑二：目录失效

当某个节点不可用时，目录要能失效，并让后续调用重新定位。

验收标准：

- 节点下线后，旧 owner 不能继续被盲目复用
- 重新调用能触发新的 owner 决策
- 不会把坏地址当成永久事实

### 6.3 里程碑三：远端消息回路

让远端投递真正跑通。

验收标准：

- 本地节点发出的调用能在另一节点执行
- 结果能回传
- 请求链路里能看出 request id 贯穿

### 6.4 里程碑四：owner 语义稳定

把 owner、缓存和失效关系做稳。

验收标准：

- owner 的变化是可见的
- routing 不会在缓存和事实之间乱跳
- 单节点语义和多节点语义保持一致

---

## 7. 不要太早做什么

这部分很重要。多节点最容易犯的错，就是第一步就开始装饰复杂。

### 7.1 不要太早做完整 placement 策略

现在先别忙着把 random、prefer-local、load-based 全搬进来。

第一阶段只需要“能选 owner、能失效、能重新定位”。

### 7.2 不要太早做完整 membership 协议

不需要一上来就把故障检测、gossip、epoch、投票一股脑拉满。

先把节点是否可见、是否存活、是否能被目录排除讲清楚就够了。

### 7.3 不要太早做 gateway 集群

gateway 更像 client 入口和跨边界流量层，不是第一刀的重点。

先把节点间内部调用打通，再谈 gateway。

### 7.4 不要太早做“分布式版所有能力”

streams、transactions、state store、timer/reminder 这些能力都可以继续放后面。

现在最重要的是把“目录、路由、消息、activation”四个件接起来。

---

## 8. 验证路径怎么设计

如果这条路要走稳，验证路径一定要分层。

### 8.1 先验证单节点不退化

多节点改造以后，单节点必须保持现有演示完全可用。

验收点：

- `GetGrain` 还能跑
- activation 还能复用
- 显式卸载还能工作
- 调度语义不变

### 8.2 再验证双节点语义

在双节点模拟里，至少要看见：

- 本地调用
- 远端调用
- owner 迁移
- 目录失效

### 8.3 最后验证错误路径

多节点里最值钱的不是成功路径，而是失败路径。

要重点看：

- 远端节点失联后会不会误用旧地址
- 目录失效后会不会继续打到坏 owner
- 重新定位后是否能恢复

如果错误路径没跑通，多节点其实还没真正成立。

---

## 9. 我会保留什么，不会动什么

这一部分给结论。

### 9.1 保留单节点语义不变的

- `GrainId` 的核心表达
- 强类型引用的调用方式
- `IInvokable` 的调用协议
- activation 内部的 turn-based 调度
- 生成产物和手写壳的分离

这些东西是内核，不该因为多节点就乱改。

### 9.2 因多节点必须改变的

- `GrainAddress` 的有效性语义
- activation directory 的 owner 语义
- routing 的本地/远端决策
- runtime 的消息协调职责
- 目录失效和重新定位
- 节点可见性和故障处理

这些东西一旦进多节点，就必须从“本地假设”改成“分布式假设”。

---

## 10. 最后的判断

如果现在从 `OrleansReplicaKernel` 继续往前走，我不会先做“看起来像 Orleans 的多节点”，而会先做“单节点语义不变、目录开始有 owner、路由开始能转发、远端开始能回包”的最小分布式闭环。

这条路很窄，但很值。

因为只要这条闭环成立，后面 membership、placement、gateway、recovery 才有地方挂；否则你只是把单节点 runtime 外面又套了一层更复杂的壳。
